# Plan: Endpoints administrativos y apoderados + migración PK usuarios

## 1. Decisiones cerradas

1. **Alcance:** 2 módulos nuevos: `administrativos` y `apoderados`. Tablas reales en `database/Script.sql:63-72` y `:139-150`.
2. **PK de usuarios migrada:** `usuarios.id_usuario INT GENERATED AS IDENTITY PK` (nueva, autogenerada). `nro_carnet` se **conserva** como columna `UNIQUE NOT NULL` (dato, ya no PK).
3. **FKs migradas:** `administrativos.id_usuario`, `apoderados.id_usuario` (y también `asesores`, `estudiantes`, `asignacion_rol`) pasan de `REFERENCES usuarios(nro_carnet)` a `REFERENCES usuarios(id_usuario)`.
4. **Creación FK-only:** `POST /administrativos` y `POST /apoderados` reciben `id_usuario` ya existente; no crean usuario en cascada. Verificación previa `SELECT 1 FROM usuarios WHERE id_usuario=$1` → `409 "El usuario no existe"`.
5. **Protección:** todos los endpoints con `authMiddleware` (Bearer o cookie `jwt`), como `src/routes/asesores.routes.js:18-22`.
6. **Patrón a replicar:** `asesores.controllers.js` + `asesores.routes.js` + `asesoresValidators.js` + `validateRequest` + `try/catch → next(error)` → `errorMiddleware` (`23505/23503→409, 22P02→400`).
7. **Chequeo previo en DELETE:** bloqueante, responde `409` específico antes de borrar (ver §6).

- Todo `WHERE nro_carnet = $1` por PK → `WHERE id_usuario = $1` (`getById`, `update`, `delete`, `authMiddleware`, `login` por id).

## 6. Chequeo previo en DELETE (bloqueante, 409 específico)

Patrón: `SELECT 1 FROM <hija> WHERE <fk>=$1 LIMIT 1` → si hay filas, `409` con mensaje claro; si no, recién `DELETE`. Mismo estilo que `checkFKs` de `capacitaciones.controllers.js:24-34` / `estudiantes.controllers.js:26-36`. Ningún `DELETE` actual lo hace (`materias:54-63`, `capacitaciones:80-89` borran directo); estos 2 serán los primeros con guarda.

- `DELETE /api/apoderados/:id`:
  ```sql
  SELECT 1 FROM estudiantes WHERE id_apoderado = $1 LIMIT 1;
  -- si existe → 409 { "error": "No se puede eliminar: el apoderado tiene estudiantes asociados" }
  ```
  Justificación: DDL `ON DELETE SET NULL` (`Script.sql:170-174`); sin guarda se huérfana estudiantes silenciosamente.
- `DELETE /api/administrativos/:id` (doble guarda, en este orden):
  ```sql
  SELECT 1 FROM mensualidades WHERE id_administrativo = $1 LIMIT 1;
  -- si existe → 409 { "error": "No se puede eliminar: el administrativo tiene mensualidades asociadas" }
  SELECT 1 FROM inscripciones WHERE id_administrativo = $1 LIMIT 1;
  -- si existe → 409 { "error": "No se puede eliminar: el administrativo tiene inscripciones asociadas" }
  ```
  Justificación: `mensualidades` es `RESTRICT` (`:589-593`) — sin guarda la BD igual rechaza vía `23503→409` pero con mensaje genérico; `inscripciones` es `SET NULL` (`:193-196`) y sin guarda deja huérfanas. La guarda previa da mensaje específico por tabla.

Orden dentro de cada `deleteController`: 1) validar `:id` numérico → `400`; 2) existencia del padre → `404`; 3) guardas hijas → `409`; 4) `DELETE` → `204`.

## 9. Riesgos

- `database/Script.sql` y `SCRIPTS de prueba.sql` aún referencian `nro_carnet` como PK (`WHERE nro_carnet = 10`); actualizarlos o el seed fallará contra la nueva PK.
- `mensualidades RESTRICT` vs `inscripciones/estudiantes SET NULL`: las guardas §6 unifican el comportamiento en `409` explícito, pero si a futuro se quiere borrado en cascada lógica habrá que cambiar guardas por reasignación.
- `celular` sin formato normalizado (solo `max(20)`); si se requiere formato telefónico, agregar refine zod.
